まとめ

今回はっきり基盤側へ降りた。DB インデックス、DNS キャッシュ、分散トレース、HTTP メソッド、EC2 の実料金——公称値や通説を鵜呑みにせず自分で測って内部を理解する記事が一群になった。エージェント運用は「回す」より境界の引き方——実装や一次調査は AI、判断と知識の構造化は人間——へ関心が移り、社内知識を Skills に固めると Notion 都度検索を定量で上回るという実測が象徴的だ。検証系はレビュー187件の分類（バグは5件に1件）や VRT の設計判断で「正しさ確認から観点と機構の設計へ」を続け、設計は概念の切り方・図とコードの同期・境界と依存方向で固める方向。そして先週まで手薄としていたユーザー解像度・プロダクトの芯（本質ニーズ、MVP を実験と定義し直す、マイクロコピー）が NN/g と Goodpatch で入ってきた。逆に、前回厚かった AI 規制・雇用といった社会・制度のマクロ視点は今回ほぼ拾えていない。

エージェントに任せる境界 ― 実装はAI、判断と知識設計は人間

エージェントを「動かし続ける」関心が、今回はどこまで任せ、人間は何を握るかという境界の設計へ寄った。象徴は松尾研究所の実験で、AI Agent を「優秀だが未オンボーディングの新入社員」と捉え、社内 Notion のオンボーディング文書を Codex の Skills（SKILL.md＋references）に構造化した。自由回答型の Eval 15課題を LLM-as-a-judge で採点した結果、項目正解率は「知識なし 33.0%→Notion 都度検索 87.3%→Skills 96.0%」、致命的誤り率は「100%→42.2%→15.6%」まで下がり、しかも応答時間は Notion 比 36% 短く入力トークンは 78% 少ない。都度検索の不確実性を、事前に構造化した知識で置き換える設計が定量で勝った。

  • 任せた先の役割分担も言語化が進む。Anthropic の Boris Cherny が示す開発者5アーキタイプ（プロトタイパー／ビルダー／スイーパー／グロワー／メンテナー）は、約40万セッションの分析で「人間が計画判断の70%、AI が実装判断の80%を担う」構造を背景に持ち、5分類を固定の職種でなくチームの能力ポートフォリオを診断する軸として使えと説く。AI が実装コストを下げるほど、問題を見つけ方向を決め品質を判断する人間側の価値が上がる、という読みだ。
  • 現場の一次事例も同じ形。本番障害のトリアージ（アラームは本物か・原因は何か・誰が影響を受けるか）を AI が24時間自動化し、午前2時33分のアラームに13分35秒で原因特定まで到達、人間は「完成した診断を読み、基準を精査し、最終決定を一文で下す」役に絞られる。クローズ済みチケットのアーカイブや新規プレイブック案の人間レビューといった継続学習まで組み込む。

AI生成物を「書いたら直る」機構で整える

「モデルの判断に毎回頼らず、機構でフィードバックを返す」線が、今回はいくつもの実装として並んだ。日本語明晰化プラグイン meiseki は、CLAUDE.md の指示がモデル判断を経由して毎回守られる保証がない問題に対し、hook でループを組む。PostToolUse hook が decision:"block" と reason を返すと reason が Claude に差し戻され、prettier の LLM 版のように機能する。textlint による決定論的検出と LLM による文脈修正の二層のうち決定論層だけを hook に切り出し、同一ファイルへの block は2回まで・textlint 不在時はフェイルオープン・環境変数で無効化、という安全弁3つで暴走を止める。

  • UI 実装の側でも同じ発想が体系になっている。MOSH はデザインデータ・ガイドライン・Storybook の分散をエージェントが辿れるよう *.stories.tsx の JSDoc に Figma/Notion の URL を書き（Storybook MCP 経由）、Agent Skill を design-context／design-review／design-principles に分け、繰り返す指摘は Biome＋GritQL のカスタム Lint（no-badge-utility 等）で CI Fail させて機械的に弾く。人の記憶でなく Lint と Skill で品質を固定する。
  • 成果物を直す往復そのものを機構化する道具も来た。Velq は AI が吐いた Markdown/HTML を「見たまま」クリック編集して元ファイルへ書き戻す WYSIWYG エディタで、文言修正なら触っていないバイトを1バイトも変えない非破壊設計と、他人の .velq を connect-src 'none' で開く多層サンドボックスを持つ。Playwright＋LLM でスクショ付きガイドを自動生成し、spec の再実行で Locator 取得失敗や画像差分からプロダクトとの乖離を機械的に検知する事例（更新が半日〜1日→15〜30分）も同じ棚だ。
  • 4本に共通するのは、AI の出力を賛美も放置もせず、hook・Lint・spec・エディタという仕組みで矯正・追従・修正する態度。「規約より機構で当たる」が具体的な実装群として厚くなった。

設計を「概念」と「構造」で決める

設計を感覚でなく共有可能な形に落とす関心が、今回は概念の切り方まで遡った。「概念設計がコードの命運を左右する」は、EC の注文 Order が配送状態まで持つモデルだと配送破損の再送を「0円の偽 Order」で表す羽目になり、売上集計・返品・推薦の各所に「0円を除外する」負債が申し送られると示す。対して「何をいくらで買ったか＝Order」「その約束をどう履行したか＝Fulfillment」を別概念に切ると、破損は失敗 Fulfillment を足すだけで自然に表せ、後から来た分割発送すらモデルを変えず実現済みになる（適切な概念設計は未来の仕様を先取りする）。SUM(quantity) がそのまま正しい意味を持ち、危うい条件分岐が消える。

  • その概念を古くさせない機構も出た。DDD の SUDO モデリングのドメインモデル図／オブジェクト図が draw.io ですぐ陳腐化し AI とも相性が悪い問題に対し、「モデル図＝コンポーネント、オブジェクト図＝Story」と捉え TypeScript の型からモデルをコードで書き WebUI に描く domain.storybook を作る。型が変わればコンパイルエラーで図が構造的に古くならず、AI にパターンを量産させられる。ERP 開発記（TanStack Start＋Hono＋oRPC＋Cloudflare Workers）も同じ構造志向で、月末集中の書き込みに D1 でなく PostgreSQL＋Hyperdrive を選び、必要な所だけ pg_advisory_xact_lock で直列化、EVM の7指標がまとめてズレないよう計算を1箇所に集約、契約 package を最奥に置いて依存方向を CI で検査する。
  • 俯瞰の足場としては『ソフトウェアアーキテクチャの基礎』が、知識を「知っていること／知らないと知っていること／知らないと知らないこと」の3層に分け、アーキテクトは専門の深さを一部手放してでも「5つの解決策を知っている」幅を取れと説く（0→1 の設計に人間の価値が残る、と AI 時代へ接続）。Strategy パターンで決済処理を開閉原則・単一責任に沿って組み替える一本も、AI 生成コードを評価する地力としての設計原則、という同じ棚だ。
  • 共通するのは、設計を概念の境界・図とコードの同期・依存方向・トレードオフの語彙という共有可能な構造に落とし、AI が量を出す時代に判断軸を人ごとにブレさせないこと。

基盤を自分で測って理解する ― DB・DNS・可観測性・HTTP

今回いちばん厚くなったのが、基盤の内部を公称でなく自分で測って理解する一群だ。DB インデックスの記事は、フルスキャンが100万件なら最大100万回チェックする一方 B-Tree は「1000件で約10回、100万件で約20回、10億件で約30回」と、データが1000倍でも比較が約10回しか増えないことを数値で示し、EXPLAIN ANALYZE で Seq Scan が Index Scan に変わる様子を実演。関数適用・中間/後方一致 LIKE・否定条件・低カーディナリティで効かないこと、複合インデックスの左端プレフィックス規則まで押さえ「念のため貼る」を明確に誤りとする。

  • 規模の側では Cloudflare の 1.1.1.1 が圧巻。2500億超のキャッシュエントリは1バイト削るだけで全体250GB以上が浮くため、不変性を使った容量情報の排除・レコードの4/16バイト化など5段階の最適化で、1件あたり953→420バイト（56%減）・全体で約100TB（サーバー約130台分の RAM 相当）を節約し、書き込み43%向上・検索19%短縮まで得た。可観測性では OpenTelemetry を Docker Compose で3層に立て、Java Agent の -javaagent だけで自動計装し Baggage の session.id を横断させて TraceQL で追う実践が、1操作＝5スパンとして可視化されるところまで手を動かす。
  • 通説を実測で覆す姿勢も健在。EC2 の購入オプションを東京リージョンで試算すると、3年全額前払い$37.23がスポット$40.37より安い——需要の高い東京ではスポットも高止まりするため「スポットが必ず最安」は成立しない。HTTP の新メソッド QUERY（RFC 10008、ボディを持てる GET）を FastAPI で動かすと OpenAPI に requestBody が出ない落とし穴があり、キャッシュは全て自作が要ると分かる、という「実際に試したら」系も同じ棚だ。
  • 5本に共通するのは、基盤（DB・DNS・トレース・HTTP・コスト）を抽象のまま受け取らず、数値・実演・試算で内部の挙動を確かめること。ツールの公称値を鵜呑みにしない慎重さが、今回は基盤の深掘りとして現れた。

AIで作れる時代に残る「人間の芯」 ― 検証・本質ニーズ・違和感

プロフィールで手薄としてきたユーザー解像度・プロダクトの芯が、今回まとまって入ってきた。Goodpatch の記事は、生成 AI に「お出かけアプリ」を頼むとありふれた一般解しか出ず試行錯誤も類似案に終わったが、発案者の「5歳の子を持つ母親」という背景に立ち返り、表面ニーズ（お出かけ先探し）から本質ニーズ（子どもの将来につながる体験）を掘り当てて初めて方向が定まったと語る。結論は、コンセプトの言語化は AI の有無に関わらず不変で、プロトタイプが検証ツールから探索ツールへ変わった一方、ユーザー理解に割く時間はむしろ増やすべき、というものだ。

  • プロダクトの型としては NN/g の2本が芯を補強する。MVP を「単に機能を削ったローンチ」でなく構造化された実験と定義し、バリュープロポジション仮説とソリューション仮説の2つを検証して意見頼みの議論をエビデンスに置き換える。情報提供型マイクロコピーは、明確さ→簡潔さ→個性の3つの C を優先順位付きで評価し（WHO がタイトルから冠詞 the を削って流し読みと検索表示切れを改善、等）、細部の言葉づかいまで設計対象にする。どちらも「作る前・作った後に何を確かめ、どう伝えるか」を人間の仕事として残す。
  • 裏返しの警戒もある。「AIっぽくないアウトプットが求められる」は、AI 製と見抜かれることが手抜き感・信頼低下を生むとし、AIっぽさの正体を完璧さと矛盾の同居・文脈の希薄さ・学習パターンの認知の3点に整理する。量産できるからこそ、文脈と人間味という芯が差になるという主張で、上の3本と表裏だ。
  • 4本に共通するのは、AI で量産できる時代に、何を検証するか・誰の本質ニーズか・どう伝え人間味を残すかという価値の芯は人間が握る、という線。作り手偏重だった関心が顧客解像度の側へ開いた。
