続報意思決定モデルは比較と実装の作法を問う段階へ

前号で中心だった意思決定モデル（System One）は、今号では話題が「これは何か」から「他とどう違い、どこに差すか」へ移った。Jev は 1.14.0 で画像入力・最大 262k トークンの長文脈・物体位置を 4 辺で返す box 型を「danger zone」ヘッダー下の実験機能として足したが、開発元自身が「マルチモーダルはテキストより性能が落ちる」「公開ベンチを絶対視するな」と釘を刺す。OpenAI も同型の Decisions API（gpt-6-luna、公開ベータ）を出し、分類・振り分け・採点に用途を絞って確率と confidence を返す。横断比較の記事は、Jev・Clef・d1・Jeff・Kev を「非公開ホスト型／27B＋LoRA／小型オープン／エンコーダ型」の 4 構造に分け、出自の違うレイテンシ（Cloudflare が測った Jev の中央値 524.1ms は公称上限 500ms を超える）は比べられないと切り分ける。

  • OpenAI の Decisions API は、レシート 48 件の分類実測で同じ gpt-6-luna の Responses API（Structured Outputs）に対し、精度 48/48 を保ちつつ中央値で約 8 倍速く（195ms 対 1,600ms）、料金は 6 割（1000 件 $0.033 対 $0.053）だった。確率と confidence が返るので「0.6 未満は人に確認」のような分岐をそのまま書ける。
  • LLM-as-a-Judge の比較では、Jev は入力 $0.042/MTok・出力無料で、Gemini 3.5 Flash Lite の入力の約 1/7。DeepEval は eval_mode="system_one" の指定だけで Jev をジャッジに差し替えられる。
  • 通常の LLM に構造化出力で enum を選ばせても候補は有限に絞れる。意思決定モデルとの差は、各候補の確率が返ることと、出力を課金しない方式にある、という冷静な整理も繰り返し出てくる。

音声認識・音声対話が低遅延・オープン・端末内へ広がる

今号で新しく太くなったのが、音声認識・音声対話の実装がオープン化・低遅延・端末内へ同時に進む動きだ。IBM は Granite Speech 5.0 を Apache 2.0 で公開し、英語 WER 平均 5.06%（公開モデル中 2 位）、日本語を含む翻訳、最大 2000 語のキーワード指定、話者識別の誤り率約 7% 低下まで備える。SpaceXAI の Grok Voice 3.0 は Artificial Analysis の Speech to Speech Index で 86.9 の首位、最初の音声まで平均 0.81 秒と GPT-Live-1（1.34s）・Gemini 3.8 Live（1.35s）より約 40% 速い。そして個人 OSS の Hayamimi（早耳）は、GPU もクラウドも使わずCPU のみ・メモリ 2GB 未満で、テレビ放送の日本語 CER 3.8%・実時間の 10〜50 倍速を達成する。

  • Hayamimi は発話ごとに言語を判定して専用モデルへ振り分け、2 秒の無音後に再デコードする二段パスで日本語 CER を 15.5%→12.0% に改善する。話し終えて約 100ms で確定し、OBS オーバーレイや WebSocket 入力まで含む。
  • クラウドの大規模モデル（Grok Voice・Granite）と端末内の軽量モデル（Hayamimi）が同時に前進している。前者は顧客サポートコールの解決、後者はライブ字幕のような「手元で完結させたい」用途を狙う。
  • ベンチの出し方は様々だ。Grok は自社に有利な τ-Voice で 71.6%、Granite は公開テストで 2 位、Hayamimi は実放送の CER と、測り方の違いに注意が要る。

検索と RAG の基盤がオープン化と低価格でそろう

検索と RAG の土台が、オープンモデルと低価格 API で一気にそろった。NVIDIA は Nemotron Retriever に埋め込み・再ランク・PDF 整形の 5 モデルを追加し、すべてオープン（OpenMDW-1.1）で公開した。DeepSeek は自社検索エンジンの検索 API・フェッチ API を1000 回成功ごとに 0.75 ドルで開放し、競合より安い。実務比較では、ローカルの EmbeddingGemma 2 とマネージドの Gemini Embedding 2 を 768 次元で揃えて測り、精度は Gemini が上（ベトナム語テキスト検索 hit@1 で 82% 対 70%）だが、EmbeddingGemma も hit@5 で 95% 超と一次絞り込みには十分と結論する。

  • 使い分けの軸は精度でなく運用だ。データを外部 API に出せない・従量課金を避けたい・GPU があるならローカルの EmbeddingGemma、手軽さと最高精度なら Gemini API、という線引き。CPU だと 1 入力 15.4 秒かかるので画像検索に GPU は前提になる。
  • NVIDIA の埋め込み 8B は Qwen3-VL-Embedding-8B や EmbeddingGemma-2 を上回るベンチを示し、rerank と組み合わせてコストを抑えつつ精度を上げる構成を勧める。
  • DeepSeek のフェッチ API は URL を渡すとページ内容を Markdown で返す。Claude Code や Codex で DeepSeek API を使うと、サーバー側ですでに検索・フェッチが走っている。

続報AI 出力を検証可能にする ― 文章・UI・社内ログ

AI 出力を検証できる形にする態度は今号も厚く、文章・UI・社内ログに具体化した。日本語の AI 臭さを扱う skill は、59 項目の癖のうちはっきり AI らしい 25 項目に★を付け、人 40 本と AI 40 本（Gemini 3.1 Pro・GPT-OSS 120B・Claude Sonnet 4.6）で見分けやすさ（AUC）を測る――★の合計 0.91・太字 0.89 に対し、英語で代表的なダッシュは日本語では 0.51 とほぼ効かない。別の skill は文の難しさを係り受けの距離・単語頻度・長さで点数化し、法律の条文をプログラム風（import/if）に構造化してから組み直す。一方で「モデル性能が 10 の位、プロンプトやスキルは 1 の位」と、素のモデル性能（日本語では Gemini を推す）に賭ける反論も出た。

  • 文章 skill は、数えられる癖（太字・ダッシュ・語尾の連続・文長のばらつき）を Python で機械的に数え、書き直した後にもう一度走らせて★が残らないことを確かめてから返す。英語向け humanizer の翻訳では日本語の癖にほとんど当たらなかった。
  • 読みやすさの skill は、文を切るだけで 122 点→45 点未満に下がるが、専門用語を言い換えると係り受けは下がっても意味が劣化して点数が上がることもある、と限界まで正直だ。構造の難しさは文の点数に出ないので、文をまたぐ指示語と新出語の「つながりの点数」を別に作る。
  • 社内の Slack/GitHub/会議メモからブログ題材を探す仕組みは、「事実で決まること（顧客案件か、機密度）はモデルに任せず、モデルには同じ主題かだけを聞く」と境目を引く。GitHub のコミットだけを根拠にせず、本人の発言で仕事の中身を確かめる。
  • OOUI の設計原則を Agent Skill にして同じお題で UI を生成させると、メニューが機能単位からオブジェクト単位に変わり、構造の採点は 8/10→10/10 に上がった。ただし機能数や完成度は変わらず、動いたのは構造だけだった。

設計とデータの基礎を数字と型で持ち直す

AI が実装を書く時代でも、設計とデータを数字と型で持ち直す棚は続く。障害とキャパシティの一本は、下流が遅くなるとスレッドプールが尽きて無関係なエンドポイントまで倒れる現象を、リトルの法則 L=λW で計算してから実測で確かめる。タイムアウト・トランザクション境界・バルクヘッド・サーキットブレーカーを 1 つずつ足し、それぞれが L・λ・W のどれを変えるかを分解する徹底ぶりだ。dbt のデータ品質「4 層モデル」を TypeScript+Zod のクリーンアーキテクチャに対応づける一本は、設計（transform）・契約（parse）・テスト・監視が普段バラバラにやっていることの集約だと示す。本番 DB に不要レコードを数千万件作ってしまった復旧記は、原因は単純な実装ミスでも、残ったデータを直す大変さは釣り合わないと痛感させる。

  • リトルの法則の記事は、尽きるまでの時間は遅延の長さでなく「空いている数 ÷ 到着率」で決まる（約 0.6 秒）こと、タイムアウトの下限（p99.9）が上限（プール × 使ってよい割合 ÷ 到着率）を超える下流には W でなく L（同時実行数）を絞るべきことを、計算と実測のずれ 1 本単位で見せる。
  • 数千万件の復旧は「件数でなく正しさで完了を判断する」。削除候補の作成と削除を小分けにし、作業テーブルに進捗を残して再開可能にした。テストは「処理の後、データはどういう状態であるべきか」まで決めておくべきだった、が学びだ。
  • dbt の 4 層は、上流の設計（Layer1 で date 型に確定）が堅固なら下流の契約やテストが素直に書ける、という依存関係がそのまま Web にも効く。違いは Layer4 の監視で、dbt は能動的に差分を取り、Web は実行時エラーで気づくことが多い。

運用とセキュリティを AI に任せきらず手で固める

現場の運用とセキュリティを、AI に任せきらず自分の手で固める記事も揃った。Node.js の 10 月のセキュリティリリース（High 4 件、Brotli の RCE など）に、受託 50 リポジトリ・Vercel 125 プロジェクトを Claude Code と一緒に 2 日で対応した記録は、engines 一括 PR を 66 本作りつつ、本番ビルドの Prisma 生成漏れやデフォルトブランチ取り違えまで踏んだ現実を残す。GitHub Pages の証明書失効（Cloudflare プロキシ配下で ACME 更新が失敗、Error 526 で約 39 時間ダウン）から Cloudflare Pages へ移行した一本は、「稀に失敗する」を運用メモでなく対策タスクにすべきだったと反省し、外形監視まで入れる。攻撃側の AI ペンテストツール Strix は、URL だけのブラックボックス診断で OS コマンドインジェクション等 6 件を 30 分・$19.77 で見つけるが、リンクされていない機能は拾えない限界も見せる。
