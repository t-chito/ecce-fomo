まとめ

ループエンジニアリングへの関心はブームの一巡を越えて批判と再定義のフェーズに入った。「自走は昔からあった、本質はむしろ外側の運用ループだ」という醒めた問い直しや、次の主戦場を意図の引き出しに置く Inquiry Engineering、そして手製ハーネスで Fable 5 を再現しようとして「単発の強いモデルに勝てなかった」実測など、賛美より検証と限界の見極めに軸足が移っている。もう一つ厚みを増したのが「AIの大量出力を信頼可能にする」検証系——自社レビュー履歴からの規約化、形式証明器やミューテーションテスト、回帰テストの設計論——で、これは先週からの一貫した背骨。加えて先週芽生えた経営・統制の視点がAI-BPR（業務そのものの再設計）へ具体化し、さらに今週は労働・トラフィック・定説の崩れといったマクロな社会視点が新たに入った。全体として、作る速さより「正しく作れているかをどう保証するか」「AIで組織と社会がどう変わるか」へ関心が開いている。

ループエンジニアリングの重心を「外側」へ ― 自走から仕組み・意図へ

先週いちばん厚かったループエンジニアリングが、今週は概念そのものを問い直す方向へ進んだ。共通するのは「ゴールまで自走するエージェント」を新規性の核に置かない姿勢だ。r_kaga は Addy Osmani・Boris Cherny の議論を引きつつ、自走するエージェントは2023年からあった発想で、いま新しいのはむしろ Software Factory＝仕事が来れば仕組みが起動し人間は設計者・監督者に回る「外側の運用ループ」だと整理する。ループを実行ループ・完了ループ・運用ループの3つに腑分けし、Anthropic 公式のターン型／ゴール型／タイマー型／プロアクティブ型の4分類に接続してみせる。この「重心は外側」という見立てが、他の記事群を貫く補助線になる。

  • 次の主戦場を「意図」に置く動きが出てきた。Inquiry Engineering は、実装や最適化のループを AI が担う以上、人間の仕事はプロンプト作成でもシステム設計でもなく本当の意図を引き出し検証することだと主張する。ユーザーニーズは直接アンケートでなく AI が行う半構造化インタビューで探り、人間は制約や証拠解釈の決定権を保持する——人間中心デザインをループの上流に接ぎ木する構図。
  • フレームワーク化も進んでいる。AI-DLC V2 はロジックを core/、実装詳細を harness/ に分離し、5フェーズ32ステージ・14エージェント（11専門家＋2レビュアー＋Composer）で回す。ユーザー承認した知見だけを project.md の恒久ルールへ昇格させる学習ループを備え、「自己申告完了させない」「曖昧さは欠陥でなく前提」といった原則を並べる。AIエージェント概論はその土台として、モデル・指示・ツール・メモリ・ガードレールの5要素、MCP/A2A、pass^k 評価、AgentOps までを一枚で俯瞰する。
  • いずれも「完了をどう定義し、外部シグナルでどう検証するか」を軸に据える点で、先週の関心をそのまま引き継いでいる。違いは、今週はループを回すこと自体より、その手前にある意図の獲得と、後ろにある知見の恒久化に力点が移ったこと。

単体では止まる ― 複数モデルで補い、しかし過信しない

ループの実装を詰めるほど、1体・1コンテキストの限界と、それを複数モデル／複数エージェントで補う設計に関心が向く。discus0434 は「賢い1体に全部やらせると失速する」経験を出発点に、Claude Code と Codex を Lead・Manager・実装・レビュー・調査の11役割へ分け tmux 上で並走させる customizable-agent-teams を紹介する。人間が対話するのは Lead 一人だけで、Lead に情報が集まりすぎると検収待ちや依頼が取りこぼされるという具体的な失敗と、その対処までを語る。モデルが一気に増えた（Fable 5、GPT-5.6 の Sol/Terra/Luna）今、「最強1つ」でなく役割ごとの割り当てで答えを出す動きだ。

  • ただしこのテーマの白眉は、複数化を賛美しない検証にある。eda_sann は Fable 5 の強み（長時間自走・初回正確性・バグ検出・委任統率・メモリ・自己検証）を Opus/Sonnet のハーネスで一つずつ再現し、別プロバイダの GPT-5.5 で評価した。結論は率直で、同等に届くケースはあるが明確に上回るパターンは無く、API で使えるなら Fable 5 単発のほうが時間・コスト・品質のバランスで有利。攻撃役の常時反証や監査が「空振り」した本数まで正直に記す。
  • atrae のデバイアス Skill は別角度から同じ不安に応える。AI に「本当にそう？」と聞いても返るのは結論の正当化なので、メインモデルの結論を隠し誘導表現を削いだうえで上位モデル（Fable 5）に同じ問題を解かせ、両者の見解を並べる。AI が理解の道具から「不安低減・責任回避の道具」に変わりつつあるという自己観察が動機として率直だ。
  • 3本を並べると、複数モデル化は「止まらないための保険」ではあっても銀の弾丸ではなく、オーケストレーションのコスト増に見合うかを毎回測る対象だ、という醒めた結論が浮かぶ。前テーマの「賛美より検証」と地続き。

スキルを「測って」育てる

先週の「スキルを書かせて育てる」が、今週は育てた結果を計測する方向へ深化した。共通の主張は明快で、スキルが効いているかは直感でなく実際の出力を測って決めろ、というもの。Syoitu の比較記事は skill-creator（公式・スキルあり/なしを「平均±標準偏差」で比較）、darwin-skill（9次元100点ルーブリックで採点し hill-climbing と git ロールバックで最適化）、SkillOpt（Microsoft・スキル文書をNNの重みのように扱い epoch・学習率・検証ゲートを実装）を並べ、まず公式で基礎効果を検証→darwin で文書品質を磨く→データセットが正当化されるときだけ SkillOpt、という段階採用を勧める。雑に書いた commit-message スキルがベースライン100%に対し92%±14%しか通らず、曖昧な指示はかえって性能を下げるという実測が刺さる。

  • LayerX の堤は、これらスキル自動最適化の研究群が「中身はほぼ深層学習の訓練ループ」だと種明かしする。訓練データ・損失関数・勾配・学習率にあたる部品を一つずつテキストに置き換えているだけ、という見立て。さらに Anthropic 公式ベストプラクティスが「広範なドキュメントを書く前に評価を作れ」と、すでに訓練ループの順番（ギャップ特定→評価作成→ベースライン測定→最小限記述→反復）を規定していると指摘する。
  • 入口の側では、Anthropic の「やって見せる」機能（画面録画＋音声でスキルを登録・再実行）が OpenAI に続いて出た。テキストで手順を言語化しづらいタスクを demonstration で登録する「show, don't tell」への収束で、スキル生成のUI自体が変わりつつある。

AIの出力を信頼可能にする ― レビューを「自社の物差し」と「決定的な審判」で

「AIが大量に書いたコードを人間がどう保証するか」という先週からの軸が、今週はレビュー側で厚くなった。方向は二つある。ひとつは汎用ツールでは拾えない自社の方言を規約化する道。estie は創業来7年分の PR レビューコメントを集計し、AIが参照できる「レビュー規約」に変換した。分析すると疑問形の指摘が3割弱、日英混在が8割、コメント長の中央値55文字——この短さと問いかけの多さ自体が自社の暗黙知で、CodeRabbit のような汎用ツールが知らない部分だという。収集・分析・蒸留・レビューの4ステップと、役割を分けた複数エージェント構成まで具体的に開示する。

  • もうひとつは人手より安く確実な審判を機械に置く道。arXiv 論文「The Prover Is the Judge」は AI に Ada/SPARK でコードを書かせ、形式証明器を自動品質ゲートに据えることで、人手レビューの約20〜40分の1のコストで TLS・暗号実装を検証・生成したと報告する。Salesforce は PR レビューコメントを AI に自動フィードバックし、6サイクル中実際にコード変更に至ったのは2サイクル、残り4は「シグナル不足で自己終了」——無限反復でなくコミュニティ標準への収束を実証した点が主眼だ。
  • 協業インターフェース側では、diff 上で AI と人間がコメントを書き合える hunk が出た。デーモンベースの CLI でエージェントがリアルタイムにコメント注入・画面操作でき、開発者が特定行に残したメモをエージェントが自動取得して実装に反映する。コピペや該当箇所探しの手間を一つのインターフェースに畳む発想。
  • 3系統に共通するのは、レビューを「人間の目視の延長」から「規約・証明・収束という検証可能な仕組み」へ移す姿勢。自己申告完了を許さないループの思想が、コード品質の側に降りてきている。

テストは量より設計 ― 肥大化に技法で立ち向かう

先週の「振る舞いの仕様としてのテスト」が、今週は肥大化とどう向き合うかという運用の悩みに具体化した。frontendflat は「コードへの不安」と「実行時間」の2つをコンパスに据える。良いテストとは開発者が安心できるか保守性に効くかのどちらかを満たすものだと定義し、Bun＋Playwright のプロジェクトで単体30ms／結合193ms／E2E 4,721ms という実測を示して、粒度と実行時間・安定性・忠実性のトレードオフのつまみを調整し続けるのが仕事だとする。両取りはできない、という割り切りが軸。

  • 「通っているテスト」の中身を疑う技法が複数出ている。ミューテーションテストは本番コードに機械的に変異（>= を > に等）を挿入し、テストが落ちなければ偽陰性を炙り出す。カバレッジを数値目標にすると AI はアサーションが緩くても行さえ通せば数字を上げにくる——Meta も行・分岐カバレッジの限界を認め、変異でテストの実効性を測る立場を取り、スケール難の解消に LLM を使い始めたという。TDD の「欠陥挿入」の自動化版として、AI 時代にこそ有用だとする。
  • 回帰テストとシステムテストは「設計された規律」として捉え直される。回帰テストの記事は、デグレの本質が共有モジュール・共通関数を伝う波及にあるとし、影響度分析と P0/P1/P2 で走らせるテストを戦略的に選ぶ。「前回 pass→今回 fail」こそデグレの重要シグナルだと説く。ST 設計の記事は、疎通確認・正常系・異常系・性能の4サイクルに分け、各サイクルの「目的」と「対象外」を明示することでスコープクリープと手戻りを防ぐ。
  • 共通する敵は「終わらないテスト」で、AI がテストを大量生産する今こそ、量でなく設計の厳密さで測り、変更との関係でテストを捉え直す——という認識が一貫する。

仕様とドメインを「構造」で守る

設計原則を AI 出力の物差しにする先週の関心が、今週はズレを構造や型で機械的に防ぐ実装へ寄った。artgraph は仕様駆動開発の「コードは変わったが仕様書は古いまま」を、LLM に探させるのでなく決定的に検出する CLI。Spec Kit や Kiro の FR-001 のような要求 ID を実装・テスト側にもタグとして書き込み、要求・ドキュメント・コード・テストの4層を紐づけ、それぞれの本文をハッシュで管理する。Claude Code の Stop Hook に仕込まれ、ターン終了時にドリフトが残れば exit 2 でブロックする——AST 由来のシンボル精度と LLM 非依存の決定性を独自性とする。

  • 型で規約を強制する動きも。Souther は業務概念を型にするコストを下げつつ「検証を通らない構築経路」「例外での却下」「業務ロジックからの直接DBアクセス」を言語の制約として禁じる小さな JVM 言語。data／invariant／behavior を .sou に書き、Java からは使えるが Souther から任意の Java API は呼べない非対称な境界で、純粋な業務計算に副作用が滲むのを防ぐ。「規約にとどまるから毎回同じ判断が要る」という問題意識が artgraph と共通する。
  • 手前の要件・設計整理の語彙も拾っている。イベントストーミング／RDRA／ICONIX の3手法比較は、業務の全体像発見・抜け漏れ整理・設計への接続という役割分担で並べる。検索画面UIの記事は、完全/前方/後方/部分一致でインデックスの効きと実装コストが変わる、ページネーションは総件数の正確さが要るか、並び替え項目が増えるほどインデックス設計が重くなる——とバックエンドが要件定義の早期に口出しすべき勘所を挙げる。bulletproof-react にオニオンアーキテクチャを重ね、feature 内部を Domain/Application/Infrastructure/Presentation に分ける実践も同じ「責務の置き場所」の関心圏にある。
