Opus 5 リリース週。最前線の受け止め方がそのまま教材になった — 発表の数字を引用する人はおらず、全員が発表当日から手元の評価装置（自前ベンチ、トレース、実タスク）で測り、「知識労働には良い、コーディングは Fable 未満、コストは重い」という発表資料に無い解像度に 48 時間で到達した。並行して「コードレビューは消えるのか」論争が燃え、Amp が plan mode を作って捨てていた事実まで開示された。前号で扱ったループ運用は「12 サブエージェントで一晩 QA」の実践報告に進み、Anthropic 自身が「システムプロンプトの 8 割を削れた」と公式に発表。制御は増やすものではなく削るものへ、という流れが公式にも合流した。

今週の最前線

Opus 5 の最初の 5 日間 — 発表の主張と、手元の評価装置

7 月 24 日に Claude Opus 5 が出た。Boris Cherny が最初に強調したのはベンチスコアではなく「これまでで最もプロンプトインジェクションに強いモデル」という system card の隅の事実で、Alex Albert は「コンサルタント並みのスプレッドシートとスライドを作る」とトークン効率を推した。ここまでが発表側の主張。

実践者側は当日から測り始めた。Dex Horthy は自前の SlopCodeBench で途中経過を実況し（同一問題で Opus 4.8 が 7 ターン、Opus 5 が 11 ターン、Sonnet 5 は 33 ターン超）、Hamel Husain は構築中の検索エージェントベンチで「burn は 4.8 の 6 倍超、GPT-5.6 の 15 倍超で、結果は両方より悪い」という測定を引いて「Evals >>>> Vibes、今こそ」と書いた。Armin Ronacher は「Opus 5 はかなり好きだ。ただ、めちゃくちゃ高くてトークン食いだ」、Gergely Orosz の周辺では「コーディングは Fable より後退」という観測。一方で Horthy 自身が「知識労働（分析・構成・CRM 仕事）には素晴らしい」とも書いており、48 時間で「どの用途に効いてどの用途に効かないか」の地図ができた。

キャリブレーション: 最前線とそれ以外を分けているのは、モデルの善し悪しの意見ではなく「発表当日に回せる自前の評価装置を持っているか」。ベンダーの数字と一般メディアの再加工を待つ側に居る限り、この解像度には到達できない。

  • bcherny: Opus 5 is our least prompt injectable model yet
  • HamelHusain: Evals >>>> Vibes, especially now
  • dexhorthy: SlopCodeBench 実況（ターン数比較）
  • mitsuhiko: expensive and token hungry
  • GergelyOrosz: コーディングは Fable 比で後退の観測

「コードレビューは消えるのか」— plan review 論争と、捨てられた plan mode

Gergely Orosz が投じた観測が発火点になった。「これまで生成コードを全件レビューしてきた堅実なベテランが、Fable 以降レビューを無意味と感じてやめ始めた。製品の急所以外は読まない」。これに対する最前線の応答は「レビュー廃止」ではなく「レビュー対象の再設計」だった。Dex Horthy は「plan review は code review を置き換えられない。code review を痛みなく速くできるようにするだけだ」と切り分け、実務側では 200 行を超える PR 全てに「変更の論理順に並べた diff tree」を自動添付する運用を公開した。読む量を減らすのではなく、読める形に変える方向。

plan mode そのものにも一石が投じられた。Thorsten Ball（Amp 開発）は「まだ plan mode を使ってる人がいるのか」と書いて燃えたあと、丁寧に整理している — 計画それ自体は正しい。ただ専用モードは不要で、「先に調査して・計画して・スケッチして」と頼めば同じ結果がより柔軟に得られる。そして Amp は plan mode を 6 週間かけて社内で作り、リリースせずに剥がしたという。前号の SpecKit 剥がしと同じ型で、「仕様書・計画書を固定資産にする」方向の実験がまた一つ、作った本人たちの手で畳まれた。Horthy の Software Factories 三部作（累計 70 万ビュー超）はこの議論の理論編で、「ベンチマークはテストを通すことに報酬を与え、保守性を壊すことに罰を与えない」以上、人間の関与を抜いた全自動工場はコード品質を蝕む、と論じる。

キャリブレーション: 「レビューをやめられるか」ではなく「何をレビュー対象にするか（計画・差分の形・急所）」が現在の問い。全件読む/全部任せるの二択で考えていたら、論争の土俵にすら乗れていない。

  • GergelyOrosz: ベテランがコードレビューをやめ始めた
  • dexhorthy: plan review cannot replace code review
  • dexhorthy: 200 行超の PR に diff tree を自動添付
  • thorstenball: Amp は plan mode を作って捨てた
  • GergelyOrosz: Kiro も GitHub Workflows も SDD は定着しなかった

ループ運用の続報 — 一晩 QA・66 ラウンドの自動レビュー・エージェント間連携

前号で扱ったループエンジニアリングは、この週、具体的な運用報告に進んだ。Peter Steinberger はリリース準備の QA をこう回している — 「OpenClaw の end-to-end QA を実 API キーでやれ。12 サブエージェントで機能を分担し、ポート別に dev gateway を立て、一部はストレステストに回せ。worktree を使い、自律的に PR を作れ。目標はバグ 200 件。毎回根本原因を直せ、対症療法は禁止」。重要なのは彼の添え書きで、「以前はこの種のワークフローはコンパクション境界で崩壊するか、モデルがチート（ズル）を始めた」— つまりこの運用が成立すること自体が新しい。同じ週に自動レビュー skill が 1 つのリファクタで 66 ラウンド回った記録も出た。

さらに一歩先の風景として、「うちのエージェントがバグを報告し、Bun 側のエージェントがその夜のうちに直した」という Bun の robobun 運用への言及がある。エージェント同士が issue tracker を介して非同期に協働する構図は、ループが単一リポジトリの内側から、プロジェクト間の境界を越え始めたことを示す。

  • steipete: massive parallel QA（compaction 境界とチートが過去形になった）
  • steipete: 実際の QA プロンプト全文
  • steipete: autoreview skill 66 ラウンド
  • steipete: robobun — エージェント間のバグ報告と修正

Anthropic 公式「システムプロンプトの 8 割を削った」— 制御は足すものから削るものへ

Anthropic が Claude 5 世代向けの context engineering 指針を公式に出した。核になる事実: Claude Code のシステムプロンプトを、性能を落とさずに 8 割以上削減できた。原則は「ルールから判断へ」（禁止事項の列挙をやめ、『周囲のコードに馴染むコードを書け』のような判断基準を渡す）、「事前情報から progressive disclosure へ」（詳細ガイドは skill に分割し、必要なときだけロード）、「CLAUDE.md は軽く」（推論で分かることを書かず、repo 固有の罠に絞る）。日本語圏では t_wada が「判断はモデルに委ね、CLAUDE.md は軽量に保ち、詳細は Skill 化して必要な時に必要なコンテクストを渡す」と要約して広めた。

これは前号の 2 つの線 — ハーネスが KV キャッシュを壊さないための「安定した prefix + 末尾追加」の原理、そして Dex Horthy の intentional compaction（「完璧な skill も計画の形も無い。context を練って形を変え、セッション間や autocompact 境界を越えて運ぶことを学べ」）— と同じ方向を向いている。プロンプトを厚くする時代の終わりを、ラボ自身が宣言した形。

キャリブレーション: 自分の CLAUDE.md やシステムプロンプトが「モデルを信用しない前提の分厚い規則集」になっていないか。削って性能が落ちるかを測る、が次の一手。

  • Anthropic: The new rules of context engineering for Claude 5 generation models
  • t_wada: システムプロンプト 8 割削減の要約
  • dexhorthy: intentional compaction

検証: 喧伝と実態

「2 人のエンジニア + エージェント軍団」— Anthropic 内部はまだ 6〜8 人チーム

言説: 開発チームはもう人間 2 人とエージェントの群れで回る。組織はエージェント中心に再編済み。

実態: Pragmatic Engineer が Anthropic 社内のソフトウェア開発を取材した記事で、Claude Platform の Head of Engineering、Katelyn Lesse 本人がこう答えている — 「『2 人の人間とエージェントの群れ』という話を聞くが、我々はそこにいない。今もチームは平均 6〜8 人だ」。最も AI 漬けの会社の内部実態がこれで、変わったのは頭数ではなく仕事の中身。同じ週の swyx の観測が変化の実際の所在を突いている — 「AI ネイティブな IC・プレイングコーチには猛烈な強気市場、『Head of なんとか』型マネージャには猛烈な弱気市場。エージェント 10 体を 1 年管理した経験 > 人間 10〜100 人を 10 年管理した経験、という乱暴な単純化すら成り立ちつつある」。Gergely Orosz は同時期に、スタートアップの CTO / VPE が数ヶ月で燃え尽きて辞めていくトレンドを報告しており、絞られているのは組織図の人数ではなく特定の役割だと分かる。

較正: 「チームがエージェントに置き換わった」はまだ実態ではない。実際に起きているのは役割の中身の組み替えと、その評価市場の急激な分岐。

  • GergelyOrosz: Anthropic 内部取材 — still 6-8 people teams
  • swyx: AI ネイティブ IC は強気市場、Head of X は弱気市場
  • GergelyOrosz: CTO / VPE の離脱トレンド

「SaaS はエージェント内製で置き換えられる」— Linear に出戻った現場

言説: コード生成が安くなったので、チケット管理も監視も feature flag も内製して SaaS を解約できる。

実態: 実際に内製へ移行したチームの続報が出た — vibecoding した社内ツールの維持がプロダクト開発の時間を食い潰し、Linear に出戻った。Gergely Orosz の整理: 「再構築は楽しい演習だが、アップデートとオンコールを自分の問題にしたいのか?」。企業利用なら SSO・RBAC・コンプライアンス認証の維持が毎年続く、という指摘も並ぶ。作るコストは劇的に下がったが、所有するコスト（保守・当番・監査）はほぼ下がっていない。

較正: 「作れるか」で判断せず「所有したいか」で判断する。内製置換の損益分岐は生成コストではなく運用コストで決まる。

  • GergelyOrosz: vibecoded 内製ツールから Linear へ出戻り
  • GergelyOrosz: 内製の compliance 維持コスト
