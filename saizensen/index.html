まとめ

作業を制御するために自分で作った仕組みを、維持の手間か融通の利かなさが上回ったという理由で外す。今週はこれが三件重なった。コーディングエージェント Amp は計画専用モードを社内で 6 週間動かしたうえでリリースせずに消し、Anthropic は Claude Code の指示文を 8 割以上削り、和田卓人は仕様書を正本とする運用をやめた。三者とも、計画や規則そのものを否定してはいない。外したのは、それを持ち続けることの方である。

今週の最前線

Amp は計画専用モードを作り、出さずに消した

Amp（AmpCode）はコーディングエージェントの製品で、Thorsten Ball はその開発側にいる。彼によれば、Amp にも計画専用モードは存在した。6 週間、社内だけで動かし、リリースせずに削除したという。本人の投稿による自己申告で、何が問題だったかまでは書かれていない。

彼が否定しているのは計画ではない。「計画が悪いとも、計画するなとも言っていない。専用モードを使ったことがないだけで、『先に調査して、計画して、スケッチして』と頼めば同じ結果が得られるし、そちらの方が融通が利く」と書いている。捨てたのは、計画という工程を製品の状態として固定すること。取ったのは、そのつど言葉で頼む側の自由度である。

  • Thorsten Ball（2026-07-27） / 同・補足

Anthropic は禁止事項を消して、判断に賭け直した

Claude Code のシステムプロンプトを 8 割以上削除し、コーディングの評価に測れる劣化は出なかったという。消した例が具体的に出ている。旧版は「コードでは既定でコメントを書くな。複数段落の docstring や複数行のコメントブロックは決して書くな、1 行まで」。新版は「周囲のコードのように読めるコードを書け。コメント密度、命名、書き方を合わせろ」。

興味深いのは、記事が古い判断を間違いだったとは書いていないところである。以前のモデルではこの手の禁止がないとコメントが的外れになることが多く、その代償を承知で受け入れていた、と書いている。つまり捨てたのは、最悪の場合を潰すための固定的な禁止。取ったのは、文脈からモデルに決めさせることと、そのぶん外れる可能性である。

  • Anthropic「The new rules of context engineering for Claude 5 generation models」（2026-07-24）

和田卓人は、仕様書を正本にする運用をやめた

詳細な設計書からコードをいつでも再生成する、という実験がうまくいかなかったと書いている。理由として挙げているのは、文書間の整合性を保つのはコードの整合性を保つより難しい、という点である。

戻した先も書かれている。文書が要らないくらい綺麗なコードを書かせ、コードに書けないこと——なぜそうしたか、なぜそうしなかったか——だけを文書に残し、全部をバージョン管理する。数日後には、計画モードと仕様駆動の違いは「作られた仕様書をどう扱うか」に絞られる、と整理し直している。仕様書を議論の道具として使うか、正本として保守し続けるか。後者は開発期間が長く分量が増えるほど綻ぶ、というのが彼の見立てである。

  • 和田卓人（2026-07-10） / 同（2026-07-14）

検証: 喧伝と実態

「計画と仕様を整えればエージェントは自走する」

広く言われているのはこれで、今週外された三つは、どれもこの方向に作られた仕組みだった。ただし外した本人たちは、計画も仕様も要らないとは言っていない。Amp は頼み方に戻し、和田は計画モードでの議論と ADR に戻している。彼らが手放したのは、計画や仕様を作ることではなく、それを維持し続ける対象として抱えることの方である。

自分の運用でどちらをやっているかは、はっきり分かれる。仕様書とコードがずれたときに、どちらを直すか。仕様書の方を直しているなら後者にいる。

  • 和田卓人（2026-07-14） / Thorsten Ball（2026-07-27）
