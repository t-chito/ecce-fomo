まとめ

Dex Horthy が「Why Software Factories Fail」で示したのは、コーディングモデルの採点機構そのものの欠落だった。SWE-bench Multilingual の 1 タスクは FAIL_TO_PASS と PASS_TO_PASS の合否だけで 1 か 0 を返し、どう到達したかは採点されない。保守性を壊すことへのペナルティは、報酬関数の中に存在しない。

同じ 7 月、Peter Steinberger らの autoreview skill の SKILL.md が公開された。450 行のうち、バグの見つけ方に割かれた分量はごく一部で、大半は「見つけた後にどこまで直してよいか」の権限規定である。スコープの凍結手順、2 サイクル未収束での停止、diff が元の 2 倍を超えたら報告して止まる、といった数値つきの停止則が並ぶ。

この 2 本は対立して見えて、実際にはレイヤーが違う。Horthy が「人間の steering が要る」と言った部分が、レビュー時点の対話から、事前に書かれた契約文へ移動している。そして Anthropic は同じ月に Claude Code の system prompt を 80% 超削除したと書いている。削られたのは能力に関する規則で、autoreview が書き足したのは権限に関する規則である。

深掘り 1｜訓練の側

保守性には速いオラクルがない ― SWE-bench の 1 タスクを解剖する

Horthy は 2025 年 7 月に自社（HumanLayer）で lights-off 運用に踏み切った。仕様とチケットだけ読み、小中規模はすべてバックグラウンドエージェントに投げる。1 回目に詰まったときは「速度に見合うダウンサイドリスク」として飲み込み、11 月の 3 回目で作り直しを決め、共同創業者が VS Code（Cursor ですらなく）で 2 週間かけてパターンを手で引き直した。この失敗の原因を、彼はハーネスの調整不足ではなくモデル訓練の構造に帰している。

その論証の核が、ベンチマークの採点手順の分解である。SWE-bench Multilingual のタスクは Redis、jq、Django のような OSS から掻き集めた 1 件あたり 15 分程度の作業で、報酬は次の 2 ビットだけで決まる。

  • FAIL_TO_PASS ― 直せと言われたものを直したか
  • PASS_TO_PASS ― その過程で他を壊さなかったか

具体例として挙がるのが fastlane の fastlane__fastlane-19304 だ。zip アクションが 2 つの optional パラメータを受け取ってすぐ .empty? を呼ぶので、include と exclude を省いた瞬間に 'zip_command': undefined method 'empty?' for nil:NilClass で落ちる。人間が実際に入れた修正は params[:include] || [] の 2 行である。

採点はこう回る。モデルは修正直前の base commit と、バグ報告（上のエラーメッセージ）だけを渡される。golden patch も、採点者として機能する test patch も見せない。そして評価側は次の順で処理する。

  • モデルが出したパッチは残す
  • テストファイルへの編集はすべて捨てる ― 失敗するテストを黙ってコメントアウトしたり、テストを無意味にする mock を差し込む個体が実際に捕まっているため、と Horthy は書いている
  • ベンチマーク側の test patch を上から当てる
  • 既存の zip テスト（PASS_TO_PASS）と新規テスト（FAIL_TO_PASS）を両方走らせ、通れば 1、それ以外は 0

ここから出る帰結は 1 行である。どうやって正解に到達したかは採点されず、保守性を削ることへのペナルティがない。だから全部を try/catch で包む書き方も、型システムの利得を潰すキャストも、報酬の上ではまったく無傷で通過する。

なぜ RL 側でこれを直せないのか。テストは数秒で合否を返すから、モデル世代ごとに何百万ループも回せる。一方で悪い設計のコスト関数が返るのは数週間から数年後 ―― 誰かが 1 行直すつもりでそのファイルを開き、同じ編集を 11 箇所に入れる羽目になり、3 ファイル先が静かに壊れていないか祈る、その瞬間である。そのインシデントを、それを引き起こした設計判断まで backprop する経路がない。Horthy は「モデルの保守性能力を測る良いベンチマークは存在しない」と明示し、自分にもそれを証明できないと断っている（脚注では、gpt-5.5 xhigh に見事なリファクタをさせられるのは事実だが、そう指示するには自分のコードベースを理解していなければならない、と補足している）。

前進している評価として 3 つが名指しされている。SWE-Marathon（Abundant AI）は「Excel を全機能クローンせよ」級の約 400 時間タスクを、単一の pass/fail ビットではなく複合報酬チャネルで採点する。DeepSWE（Datacurve）は現実には作られなかった OSS 課題を使うことで訓練データ汚染を構造的に回避する（ただし品質は解かない）。Cognition の Frontier Code は複数 PR にまたがるタスクで、pre-patch のコードに対して落ちないテストを書いたらペナルティという決定論的な品質判定（mutation testing の発想）を入れ、さらに diff に対してコード品質ルールを持つ judge モデルを走らせる。それでも Horthy の但し書きが効く ―― モデルが良し悪しを確実に判別できるのなら、最初から良い方を書いていたはずだ、と。

ここから彼が引くのが天井と床の線である。レビューエージェントもトークンの追加投入も、間抜けなミスを拾うので床は上げる。だが天井は動かさない。天井は RL で教えられた分であり、良い設計はまだ教え方がわかっていない。

移植できる部品として、彼が人間を残す 4 段を挙げている。Product Requirements / System Architecture / Program Design / Vertical Slices。このうち Program Design が最も過小評価されていると言い、実装前に成果物として次の 3 種を作る。

  • call-stack tree の diff ― 制御フローの変化を + / - 付きの入れ子リストで書く
  • file-tree diff ― NEW / MODIFIED のコメント付きで、どこに何が置かれるかを固定する
  • 型とメソッドシグネチャ ― アーキ文書に載せるには内部的すぎるが、エージェントが外しうる箇所

いずれもモデルが下書きし、人間が言い争う。どれも「やらなければコードレビュー中に暗黙で決めることになる決定」であり、レビュー時は考えを変えるのが最も高くつく時点だ、というのが理由づけである。

運用の数値も具体的だ。全タスクのうち約 40% は oneshot か軽いフィードバック 1〜2 往復で済ませる。中規模はプロダクト設計とシステム設計を 1 枚の計画書にまとめ、フェーズ分割しない。大物だけ全段を通す（大規模リファクタではプロダクト段を飛ばす）。実装は 1〜3 スライスずつ投げ、100〜200 行の単位で読んで方向を直す ―― 2000 行超の向こう側で何が壊れているかわからない状態になるより安い、という判断である。手戻りの閾値は 20%：それ以上の手戻りを要する PR は提出者とレビュアの双方に知的・情緒的な負荷をかけると彼は書き、AI の oneshot PR は 50% 寄りだと見積もっている。エージェントが書いたコードベースが「重くなり始める」のは 3〜6 ヶ月というのが彼の体感値だ。

外部データとしては Faros AI のレポートが引かれている。レビューコメント数 +25%、コメント長 +22.7%、レビューを完全に飛ばしてマージされる PR +31.3%、PR あたりインシデント +242.7%、月次インシデント +57.9%、開発者あたりバグ +54%。Horthy 自身が「因果の決定打ではなく相関のシグナル」と留保をつけている点は、そのまま読者側の留保にすべきだ。結論として彼が置くのは、10〜100 倍ではなく「2〜3 倍、安全に」という目標設定である。

深掘り 2｜運用の側

レビューを自動で回している当事者が書いた、止まるための契約 450 行

autoreview は OpenClaw の agent-skills に入っている「出荷前クローズアウト用のコードレビュー」skill である。構造化レビューのヘルパーを 1 回呼ぶだけの薄い皮に見えるが、SKILL.md の実体は、エージェントに何をさせないかを列挙した契約書だ。Horthy の議論と突き合わせる価値があるのは、これがまさに「レビューエージェントを足せば解決する」側の最も真剣な実装だからである。

既定値と、エンジンを変えてよい唯一の条件。本文中に散在している既定値と閾値を一覧にする。数値と分類名はすべて SKILL.md の記述である。読みどころは 2 つ。エンジンとモデルの切り替えが許されるのは Sol へのアカウントアクセス失敗 1 件だけで、容量不足・レート制限・その他の失敗ではエンジンもモデルも切り替えてはならないと明記されていること。そして出力の既定が P0 のみ、つまり「現在の変更をブロックするに値するもの＝通常フロー・結果・安全境界を実質的に壊すもの」だけを報告する点である。

レビュー結果の格。「レビュー出力は常に advisory として扱え。決して盲目的に適用するな」。すべての指摘は実際のコードパスと隣接ファイルを読んで検証する。外部の挙動に依存する指摘なら、依存先のドキュメント・ソース・型まで読む。そして却下すべきものが名指しされている ―― 非現実的なエッジケース、投機的なリスク、広範な書き換え、コードベースを過度に複雑にする修正。受理した指摘がバグクラスやパターンを示している場合は、同じ PR のスコープ内で兄弟インスタンスを探して一括で潰すが、触った表面・オーナー境界・明らかにフォローアップ領域のところで止める。

Scope Governor ―― この skill の重心。最初のレビュー前に、スコープのベースラインを凍結する。凍結する項目は 6 つ：元の依頼または issue、対象ブランチ、意図した挙動、オーナー境界、変更ファイル、非テスト LOC。継承済みで既に膨らんだブランチでは、既存のドリフトを受け入れずに「意図した PR の diff」をベースラインに取り直す。指摘はパッチを当てる前に必ず 3 分類する。

分類成立条件処置
In-scope blocker現 diff が持ち込んだ / 同じ owner boundary / タスクの contract を変えずに直せる直す
Follow-up実在するが、隣接するバグクラス・兄弟面・清掃・広い硬化トラックに属する別 PR / issue へ
Stop-and-escalate新しい protocol / config / storage / public API contract、別の owner boundary、リリース手順の変更、元の依頼外の設計判断を要する止めて報告

そして停止条件が数値つきで並ぶ。狭い PR がアーキテクチャ変更・プロトコル変更・マイグレーション・リリースプロセス変更に化けたとき。diff が元のファイル数または非テスト LOC の 2 倍を、スコープ拡大の明示的承認なしに超えたとき。レビュー起点のパッチサイクルが 2 回回っても収束しないとき（一時停止し、残りの指摘を全部再分類してから次の編集に進む）。最善の修正が「まず正典となる契約を定義する」であって、また 1 枚ローカルな推論層を足すことではないとき。修正すると PR がもう同じ挙動・issue・オーナー境界を説明しなくなるとき。2 サイクルの一時停止のあとは、残った受理済み指摘が全部まだ in-scope blocker である場合にのみ続行する。そうでなければ、有用な分析を保存し、安全に着地できる最小の部分集合を特定し、大きい修正はフォローアップに回す。スコープ分類や焦点を絞った証明が未決のまま、レビュー起点の修正コミットを積んだり push したりしてはならない。スコープが壊れたら、それらは着地レーンから外して履歴に残さない。

スコープを爆破してよい「critical 例外」は列挙で閉じている ―― 進行中のデータ損失、クラッシュ、インストール／アップグレードの破損、リリースブロッカー、具体的なセキュリティ露出。この 5 つでなければ critical ではない、と書いてある。リリース系のブランチではさらに厳しく、ブランチ名がリリースらしくなくても freeze 規律を適用し、非ブロッキングの指摘は main 向けのフォローアップにする。「リリースブランチをリファクタのレーンとして使うな」。

失敗モードの扱いが具体的。構造化レビューはモデル呼び出しが生きている間、大きなバンドルでは 30 分かかりうる。review still running: <engine> elapsed=<seconds>s pid=<pid> というハートビート行は健全な進捗であってハングではない。2〜5 分静かだからといって、あるいは 30 分の窓の中でまだ走っているからといって、レビューを殺すな。プロセスを覗くのは、期待されるハートビートを複数回落としたとき、30 分を過ぎたとき、明らかにサブプロセスが失敗したときだけ。

秘密情報の扱いは、境界条件が読める書き方をしている。エンジン呼び出しの前に、レビュー対象の追加・変更・削除された内容そのもののスナップショットに対して TruffleHog を走らせる。ポリシーは意図的に TruffleHog の低誤検知な pre-commit ポリシー（verified,unknown）に合わせてある ―― 任意のパスワードっぽい文字列は分類しないし、変更されていない履歴を再スキャンもしない。そのスキャンを通過した後、ローカルで認識できる秘密様の値が伏字にされるのは「完全に削除されたファイルの削除行にのみ出現する場合」に限られる。同じ値が追加行・文脈行・staged/unstaged 混在のどこかに 1 つでも出たら、レビューは fail closed で落ちる。バイナリが無ければ公式のプラットフォーム中立な手順へのリンクを出して落ちる（自動インストールはしない）。CI 側でも PR で TruffleHog を回すことがバックアップとして推奨されている。

隔離のテーブルが、拒否の理由まで書いてある。実行可能なエンジンは codex / claude / pi の 3 つで、droid・copilot・cursor・opencode は fail closed で拒否される。拒否の理由は各々違う。

エンジン隔離フラグ
codex認証のみの config 上書き、隔離ワークスペース、exec --ignore-user-config --ignore-rules --skip-git-repo-check、read-only sandbox
claude--safe-mode --setting-sources user --strict-mcp-config --disallowedTools mcp__*、auto-memory とファイル/シェル系ツールを無効化、空の外部ワークスペース、WebSearch は既定で付与（v2.1.169+）
pi--no-approve --no-session --no-context-files --no-extensions --no-skills --no-prompt-templates --no-themes --no-tools（v0.79.0+ 必須）
droid拒否。project instructions とツールの両方を無効化できない
copilot拒否。リポジトリ読み取りツールが、レビュー対象バンドル外の ignored ファイルまで露出させる
cursor拒否。文書化された read 権限がホストの絶対パスを指せる
opencode拒否。project/global config の隔離と private-network fetch 拒否の両方が証明できていない

通る 3 つの隔離も細かい。Codex は上表のフラグに加えて、空の一時ワークスペースで走り、project-doc 予算はゼロ。これはリポジトリルート読み取り（ignored なクレデンシャルを露出する）より狭く、レガシーの read-only サンドボックス（ホストのファイルシステム全体を読める）より狭い、と明記されている。--ignore-user-config は exec 実行時の config 読み込みを丸ごと飛ばすが、認証だけは CODEX_HOME/config.toml から cli_auth_credentials_store・forced_login_method・forced_chatgpt_workspace_id の 3 つだけ再構成する。Claude は --safe-mode でプロジェクトの hooks・skills・plugins・MCP・CLAUDE.md が全部無効になり、ファイルシステムもシェルも無し、WebSearch だけが既定。Pi は読み取りツールがリポジトリに閉じないため --no-tools で、中立な一時ディレクトリから走らせる。

分割の保証と、その限界の自己申告。大きい diff は 8 パスを上限として境界で分割され、「元のバンドルの全バイトがパス列の中でちょうど 1 回ずつ現れる」。1 本の物理的な diff 行がパスをまたいで割れても、元の追加／削除／文脈のマーカーを保持する。そのうえで自分の限界を書いている ―― チャンク分割は 1 回のモデル呼び出しにクロスファイルの実装詳細を全部渡すことはできない。アーキテクチャ寄りの変更では、意味的な決定面が 1 パスに収まる形の PR にすべきだ、と。縮小のために lockfile・生成クライアント・ポリシー・マニフェスト・スキーマを落としてはならない。

この skill が自分の射程外だと宣言している場所。「クリーンな autoreview は、UI・CLI・API・生成物がユーザーの視点で動くことの証明にはならない」。autoreview は source-aware で変更バンドルを裁く。挙動の検証は source-blind な behavior-validator が、動いている製品を挙動契約に照らして裁く。役割が分けてある。

細部で最も印象的なのは、回帰の帰属に関する規定だ。blame されたコードの作者、blame された PR の作者、その PR のマージ者／コミッタ、現在の PR の作者、PR と日付 ―― この 5 つの役割を混ぜるな、と書いてある。blame できる PR が辿れなければ、コミット SHA・日付・作者名を出典とし、マージ者を推測してはならない。そして blame 先の PR が clawsweeper[bot] のような自動化にマージされていたら、実務的な範囲で人間のトリガーを特定する ―― タイムラインとコメントを先に見て、レート制限されていたらキャッシュや公開 PR の HTML を見る。@clawsweeper automerge や /landpr のようなメンテナのコマンド、automerge を仕掛けたラベルやステータスコメントを探す。見つかれば automerge triggered by @login と報告し、見つからなければ「trigger unknown」と書く。

停止則は最後まで一貫している。ヘルパーが exit 0 で受理／実行可能な指摘なしなら、そこで止まる。「良い『クリーン』の一文を得るため、セカンドオピニオンのため、あるいは締めの文言を綺麗にするためだけに、もう 1 回レビューを走らせるな」。パネル（複数レビュア）は opt-in のみ。レビューのためだけに push するな。diff がまるごと散文の内部メモか SKILL.md のドキュメントだけなら autoreview は必須ではない（ただしユーザー向けドキュメント、実行可能な例、設定、スクリプト、生成ファイル、挙動変更はこの免除に入らない）。

突き合わせ

天井の話と権限の話は別の話だった ― 削った 80% と足した 450 行が同じ月に共存する理由

表面上、この 2 本は真っ向から対立する。Horthy は「レビューエージェントとトークンは床を上げるが天井は動かさない、当面の判定者はあなただ、コードを読め」と言う。autoreview は別モデルにレビューさせて自動で回すための道具である。だが SKILL.md を実際に読むと、対立が想定したところに無い。

450 行の重心は、バグの見つけ方ではない。見つけ方に関する記述は「P0 のみ」「セキュリティ観点は常に含むが正当な機能を潰すな」程度で終わる。残りは、見つけた後にどこまで動いてよいかの規定である。ベースラインの 6 項目、3 分類、5 つの停止条件、2 サイクル、2 倍、critical 例外の 5 項目、リリース freeze。これは Horthy が「人間の steering が要る」と言った部分の移動先だ。レビュー時点で人間がその都度下していた「これは今直す／これは別 PR／これは設計会議」の判断が、事前に書かれた契約文に前倒しされている。Horthy 自身の言い方に翻訳すれば、これも front-loading である ―― 彼が計画段に前倒ししたのに対し、autoreview は権限の境界を前倒ししている。

一致点は、レビュアの判断を権威にしていないこと。Horthy の最も鋭い一文は「モデルが良し悪しを確実に判別できるのなら、最初から良い方を書いていたはずだ」である。autoreview のこれへの回答は「判別させない、適用させる」だ。出力は advisory、全指摘は実コードパスと隣接ファイルを読んで検証、却下すべき類型は列挙済み。オラクルはモデルではなく、人間が書いた契約文の側にある。同じ機構がいま 3 箇所に同時に現れている ―― Cognition の Frontier Code が RL 評価の中で diff にコード品質ルールの judge を走らせ、Anthropic は Claude Managed Agents（beta）で rubric に対して別の grader エージェントを走らせ失敗を自動で差し戻し、autoreview は出荷前に別モデルを呼ぶ。Horthy の反論は 3 つとも同じように当たる。当たらないのは、rubric や契約を人間が書いた部分だけである。

三点目に Anthropic の context engineering 記事を置くと、線が引ける。Anthropic は Opus 5 / Fable 5 世代のために Claude Code の system prompt を 80% 超削除し、コーディング評価に計測可能な劣化はなかったと書いている。削られた代表例が「コードでは既定でコメントを書くな。複数段落の docstring や複数行のコメントブロックを決して書くな ― 1 行まで」で、新しい版は「周囲のコードのように読めるコードを書け。コメント密度・命名・イディオムを合わせろ」。ツール使用の第 1 原則だった「例を与えよ」も撤回され、「例はモデルを特定の探索空間に閉じ込める、代わりにインターフェースを設計しろ」に置き換わった（Todo ツールで pending / in_progress / completed という列挙を出すこと自体が使い方のヒントになり、「in_progress は 1 件だけ」という指示が要求挙動を定義する、という説明つき）。Simon Willison が Cat Wu と Thariq Shihipar から拾った例も同じ方向で、「小さなコピーやデザイン変更ではテストを更新するな」と条件を切るより、テストを書くかどうかの判断自体をモデルに委ねる方が良い、という助言だった。

同じ 7 月に、autoreview は 450 行の規則を書いている。これは矛盾ではなく、規則の種類が違う。Anthropic が削ったのは能力に関する規則（どう書くか）で、モデルが賢くなれば不要になる種類のものだ。autoreview が書いたのは権限に関する規則（どこまでやってよいか、何を fail closed にするか）で、これはモデルの性能とは独立している。gpt-5.6-sol がどれだけ賢くても、「この PR のオーナー境界はここまで」「リリースブランチではリファクタしない」「cursor CLI は絶対ホストパスを読めるから使わない」は、モデルが導出できる情報ではない。記事自身がこの例外を明示している ―― 「skill を overconstrained にするな、ただし極めて重要な領域は除く」「skill は、あなた／チーム／プロダクトに固有の意見・知識・ベストプラクティスを符号化するときが最良」。autoreview の規則はほぼ全部この例外の側にある。

ただし autoreview は同じ記事の別の助言には従っていない。Anthropic は「長い skill はできる限り progressive disclosure を使い、複数ファイルに分割せよ」と書いているが、autoreview は単一の 450 行である。これは検証可能な不一致で、どちらが正しいかはここでは決まらない。決まるのは、この文書が毎回全部コンテキストに載っているという事実だけだ。

本当に対立している 1 点。autoreview の既定レビューエンジンは Codex（gpt-5.6-sol）であって Claude ではない。この skill が Claude 系のハーネスからも使われることを考えると、これは意図的な賭けである ―― 生成したモデルとは別の訓練を受けたモデルなら、天井の形も違う。Horthy の主張が正しければ、これは天井を動かすのではなく、床の形を変えるだけだ。Horthy 自身が「レビューエージェントとトークンは間抜けなミスを拾って床を上げる」と認めているので、両者は「別モデルのレビューには意味がある」までは合意していて、「それで人間がコードを読まなくて済むか」で別れる。autoreview の答えは、SKILL.md の中に既に書いてある ―― 全指摘を実コードパスを読んで検証しろ。読むのが人間かメインエージェントかは、この文書は指定していない。

どちらが自分の状況に効くかの判定。以下は YES/NO と数値で答えられる。

  • エージェントが書き始めてから 3〜6 ヶ月を超えたコードベースか。超えていないなら、Horthy の 4 段（プロダクト／アーキ／プログラム設計／垂直スライス）は過剰である。彼自身、約 40% のタスクは oneshot で通している。
  • 直近 20 本の PR のうち、手戻り 20% 超のものが半分以上か。半分以上なら、レビュー段を足すのではなく計画段を足す方が効く。レビューを速くしても、手戻りの量は減らない。
  • レビュー起点の修正が 2 サイクルで収束しているか。していないなら、残っている指摘は in-scope blocker ではない可能性が高い。分類していないだけの状態と、収束していない状態は区別がつかない。66 ラウンド回るワークフローが健全かどうかは、その 66 が「毎回何かに収束した 66」だったか、「同じ場所を 66 回叩いた」かで決まる。ログで区別できる。
  • 今の PR の diff は、元のファイル数か非テスト LOC の 2 倍を超えたか。超えていたら、そのレビューループはもう最初と別の仕事をしている。
  • 直近で受理した指摘について、「実コードを読んで検証したのは誰か」に答えられるか。答えが「誰も」なら、Horthy の言う天井の側にいる。
  • レビューエンジンは、コードを生成したのと同じモデルか。同じなら床は上がるが、天井の形は同じである。
  • あなたの skill / CLAUDE.md の中で、能力に関する規則（どう書くか）と権限に関する規則（どこまでやってよいか）を分けて書けているか。Anthropic が削ってよいと言ったのは前者だけである。

移植

自分の環境に移植する手順（最小構成から）

この skill 一式を丸ごと入れる必要はない。移植価値があるのは、スクリプトではなく契約と閾値のほうである。最小から順に積む。

段 0（0 分）: 既存の verify を先に試す。 Anthropic のガイドは、独自の検証ループを書く前に組み込みの /verify（アプリをビルドし、実行し、変更を観察する）を試せと明示している。ここで足りるなら以下は要らない。

段 1（10 分）: 契約を 1 ファイルに書く。 .claude/skills/closeout-review/SKILL.md に、以下 5 行だけ置く。これが autoreview の Contract 節から落とせる最小核。

  • 既定出力は P0 のみ。現在の変更をブロックすべき、通常フロー・結果・安全境界を実質的に壊す所見だけを報告する。
  • レビュー出力は advisory。全所見を実コードパスと隣接ファイルを読んで検証してから採否を決める。
  • 非現実的なエッジケース、投機的リスク、広範な書き直しは却下する。
  • 修正が入ったら、focused テストとレビューを両方やり直す。
  • accepted/actionable な所見がゼロで終わったらそこで停止する。報告文をよくするための再実行はしない。

段 2（5 分）: 対象選択を固定する。 「dirty ならローカル」を既定にすると、コミット後にレビューして空 diff を clean と誤読する。PR がある場合の実 base を取る形にする。

  • base=$(gh pr view --json baseRefName --jq .baseRefName) → その origin/$base を base にした branch diff をレビュー対象にする。
  • 着地済み・push 済みの単一変更は commit 指定でレビューする。clean な main を origin/main と比べても、push 後はたいてい空 diff になる。
  • base ref はローカルで解決できている必要がある（autoreview は branch レビュー中に自動 fetch しない。ここは自分の側でも同じ規約にするか、明示的に fetch を前段に置く）。

段 3（5 分）: 停止条件を数値で書く。 ここが最も移植価値が高い。文言ではなく数字にすること。

  • diff が元のファイル数か非テスト LOC の 2 倍を超えたら停止して報告。
  • レビュー由来の修正サイクルが 2 回で収束しなければ、次の編集の前に残り所見を全件再分類。
  • 所見は In-scope blocker / Follow-up / Stop-and-escalate の 3 値をパッチ前に必ず付ける。
  • 最良の修正が「先に正規の contract を定義する」であるなら、その場でローカル推論層を足すのをやめる。

段 4（15 分）: レビュアーを隔離する。 レビュー対象ブランチの設定でレビュアーが動くと、ブランチ側から出力を操作できる。Claude をレビュアーに使うなら、autoreview がやっているのと同じ組み合わせを写す: --safe-mode --setting-sources user --strict-mcp-config --disallowedTools mcp__*。--safe-mode は project hooks / skills / plugins / MCP サーバ / CLAUDE.md を無効化する。加えて、レビュアーには空の外部ワークスペースを与え、リポジトリではなく検証済みバンドルだけを入力にする。

段 5（10 分）: secret scan を engine 呼び出しの前段に置く。 追加/変更/削除された内容そのもののスナップショットに対して verified,unknown ポリシーで走らせる。PR CI にも同じスキャンをバックアップとして置く（autoreview の外側で冗長化する、と SKILL.md が推奨している）。リポジトリローカルの git hook は任意。

段 6（判断）: 起動位置を決める。 Anthropic のガイドは検証ループの起動位置を 4 つに分類し、それぞれに卒業条件を付けている。

断片

  • 検証ループの置き場所は 4 通りで、卒業の合図が決まっている。Anthropic の記事は standalone / embedded / chained / PR ゲートの 4 段を挙げ、それぞれの離脱条件を書いている。standalone を卒業する合図は「毎回の変更のあとに走らせている」こと。embedded（生成側 skill の本文末尾に検証を 1 行足す）が使えないのは、built-in skill と plugin 管理の skill ―― 更新で上書きされるため、そこは chain にする。PR 全体のゲート化はチェーンが固まるまで待て、調整のたびにチーム全体に見える事象になるから。挙げられている例が良い ―― 「backfill ステップ無しでカラムを落とすマイグレーションを却下する」は決定論的な規則だが、汎用リンタは絶対に書かない、プロジェクト固有の規則である。出典
  • その chain を、Anthropic の Claude Code チーム自身が日常で回している。同じ記事に実物が載っている ―― /code-review がバグを探し、/simplify が diff を整え、/verify skill が end-to-end の挙動を確認し、UI に触った変更なら独自の /design skill が DESIGN.md のガイドラインと突き合わせる。autoreview が 1 つの skill 内に畳んでいる closeout を、4 つに分けて連鎖させた形になっている。出典
  • progressive disclosure にはキャッシュの請求書がついてくる。Anthropic は「ツールを deferred loading にして、必要になったら ToolSearch で定義を引かせればコンテキストを食わない」と書いている。Armin Ronacher（Earendil）の解説はその裏側を扱う ―― ツール定義はシステムプロンプトに畳み込まれて会話より前に置かれるので、ツールを 1 個足す・消す・スキーマを変える・並び順を変えるだけで、最初の不一致点がプロンプトの先頭近くに移動し、その後ろの会話が全部再計算される。数千トークンのスキーマを節約して数万トークンの会話を再課金する、という形になる。逃げ道は message-anchored な additive tool loading（Anthropic 系の deferred definitions と tool_reference、OpenAI 系の tool-search item）で、これは追加のときだけ成立する ―― 削除・入れ替え・毎ターンの再構築は効かない。数字も 2 つ：Anthropic の既定キャッシュ TTL は 5 分で、多くの開発作業（ビルド、テスト、diff を読む時間）より短い。Claude Code はサブスクリプション利用者向けにこれを 1 時間に上げている、と Ronacher は同社コードベースからの観察として書いている。履歴の刈り込みの損益分岐も式で置いてある ―― 一度きりの書き直しコスト ≒ 編集後に生き残るトークン数 ×（非キャッシュ単価 − キャッシュ読み単価）、対して毎ターンの節約 ≒ 刈ったトークン数 × キャッシュ読み単価。出典: Earendil Engineering「Prompt Caching In Agents」（2026-07-22）
  • CLAUDE.md に書くべきなのは gotcha であって概要ではない。Anthropic の推奨は、リポジトリが何のためのものかを簡潔に書いたら、残りのトークンはコードベース内の落とし穴に使え（例として「型は 1 つのモノリシックなファイルに置いていて他には無い」）。ファイルシステムやリポジトリを見ればわかる「当たり前のこと」を書くな。そして spec は markdown である必要がない ―― 詳細なテストスイート、他のコードベースにあるポートすべき関数、HTML アーティファクトも spec として使える。デザインについては「説明やスクリーンショットより HTML モックアップの方が良い結果を出す」と明言している。整理用に /doctor コマンドが用意された。出典
  • モデル選択そのものを判断に委ねると、何が永続化されるか。Simon Willison は「全コーディングタスクで、適切な低出力モデルを自分の判断で選び、サブエージェントで走らせろ」と Claude Code に指示し、生成された memory ファイル（~/.claude/projects/<project>/memory/delegate-coding-to-subagents.md、node_type: memory / type: feedback）には、実装は sonnet、機械的な編集は haiku、判断・レビュー・統合はメインループに残す、という適用規則が書かれた。autoreview がレビュアのモデル切り替えを「アカウントアクセス失敗以外は禁止」と固定しているのとは、対極の設計判断である。出典
